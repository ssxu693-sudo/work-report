# 模拟评审与预测追问

---

## 一、预测对方回复

**不需要征求用户同意，但要看场合决定做不做、做多少。**

| Mode | 做不做 |
|---|---|
| M1 日报 | **不做**。三行的日报配五条回复预测是荒谬的 |
| M2 周报 | 最多 1–2 条，且只在确实有风险条目（要决策、要资源、有坏消息苗头）时做。平常的周报不做 |
| M3 项目汇报 | 做 |
| M4 述职/晋升 | 做，用第 1.4 节的五类框架 |
| M5 年终总结 | 做 |
| M6 坏消息 | **必做，且最重要** |

原则：**排场要和场合相称。**用户写日报是想赶紧交差，不是来做心理建设的。

### 1.1 为什么做

让人焦虑的从来不是坏结果，是不知道会发生什么（模糊厌恶）。

哪怕预测结论是"大概率已读不回，这很正常"，说出来本身就在降低不确定性——这就是价值。

### 1.2 格式

给 2–4 种可能反应，每种配一句应对。简短，不要写成剧本。

```
可能的反应：
· 已读不回 —— 最常见，不用多想，说明没问题
· 追问"那个 200ms 是怎么测的" —— 你回：压测环境 500 并发下的 P95，报告在 XX
· 说"下周把这个推到全量" —— 你回：需要先跟运维确认灰度窗口，我周一给你时间点
```

### 1.3 分场景重点

| 场景 | 预测重点 |
|---|---|
| M1/M2 日报周报 | 哪一条最可能被揪住问细节 |
| M3 项目汇报 | 这个数怎么来的 / 为什么不早说 / 下一步谁负责 / 还需要多少资源 |
| M6 坏消息 | 会不会被追责 / 新时间点靠不靠谱 / 为什么现在才说 |
| M4 述职答辩 | 用下面的五类框架 |

### 1.4 述职/晋升的五类提问框架

这是大厂评委提问的通用归纳，直接用：

1. **你是干什么的** —— 目标：你负责什么，为什么是你
2. **准备用什么方法干** —— 方法：方案怎么选的，为什么不选另一个
3. **实际怎么干的** —— 执行：过程中遇到什么，怎么解决的
4. **有没有干出成绩** —— 结果：数字、影响面、是否可持续
5. **下一步计划做什么** —— 规划：下个阶段的目标和路径

**两个高危区必须单独预警：**

- **个人结果 vs 团队结果混淆** —— 评委最爱在这里挖。逐条检查用户的表述，凡是"我们做了"的地方，追问他本人具体做了什么
- **缺资源约束指标**（按需，见元规则）—— 只说做成了什么、不说用了多少人多少时间，评委无法判断效率

## 二、模拟评审（可选，需询问）

### 2.1 什么时候提议开启

| Mode | 默认 |
|---|---|
| M1 日报 | 不提 |
| M2 周报 | 不提（用户主动要求才开） |
| M3 项目汇报 | 问一句 |
| M4 述职/晋升 | **建议开**，主动推荐 |
| M5 年终总结 | 问一句 |
| M6 坏消息 | **建议开** |

🔴 **检查点 C6：用户同意前，禁止自行跑迭代。**没答应就直接交付。

提议的说法要具体：

> 「要不要我扮演一遍你领导，先挑一遍毛病再给你？大厂晋升答辩前本来就建议找资深同事做模拟答辩，这个能省你去约人的功夫。大概多花两分钟。」

### 2.2 评审角色必须具体

**禁止用抽象的"上级"做评审。** 抽象角色给出的是抽象反馈，没有用。

从 `我的汇报档案.md` 取，或现场问一两句：

- 技术出身还是业务出身？（决定他会追问哪一层）
- 看数字、看风险、还是看人际？（决定他先看哪一段）
- 什么考核体系？（决定他关注哪些维度）
- 这次的读者是直属领导，还是不了解你日常的评委？（决定术语密度）

M6 场景额外设定：**刚看到坏消息、情绪不太好的领导**。

### 2.3 评分维度（固定，且全部减法导向）

**这套维度必须固定不变。** 否则多轮迭代会把稿子越优化越花哨，跑向反面。

| 维度 | 问什么 | 分值 |
|---|---|---|
| 注意力 | 11 秒内能不能抓到重点 | 1–5 |
| 信号强度 | 有几条可验证锚点 | 1–5 |
| 决策成本 | 要领导做什么是否清楚 | 1–5 |
| AI 味 | 有没有形容词代替数字、套话、对仗 | 1–5 |
| 注水率 | 有多少字是删掉也不影响的 | 1–5 |
| 贡献清晰度 | 个人和团队是否分得清 | 1–5 |
| 资源指标 | 是否说清了投入（**不适用则跳过，不扣分**） | 1–5 / N/A |

注意所有维度都指向"更短、更硬、更清楚"，所以迭代方向天然收敛，不会失控。

### 2.4 迭代规则

1. **上限 2 轮，写死。** 不许再多
2. 每轮记录改了什么、分数变化
3. **如果第 2 轮总分没有提升，回退到第 1 轮版本**
4. 最终交付时说明改了什么：「主要改了三处：把开头的背景删了直接上结果、给两条补了数字、把『积极推进』换成了具体动作」

**为什么上限是 2 轮：**

迭代过头会把用户自己的语气磨掉，磨成标准 AI 腔——那正是这个场景的死穴。我们要的是"更清楚"，不是"更光滑"。

### 2.5 评审输出格式

```
【模拟评审 · 扮演角色：技术出身、看数字、直属 leader】

基线打分：注意力 3 / 信号 2 / 决策成本 2 / AI味 3 / 注水 3 / 贡献清晰 4
总分 17/30

他会怎么想：
· 前两行在讲背景，我没耐心，直接跳到第三行了
· "优化了查询性能"——优化多少？这句话等于没说
· 看完不知道要我干什么

改完：总分 25/30
改动：结论提到第一行 / 补了两个数字 / 加了「需要你拍板」的标记
```

## 三、边界

- 模拟评审**不改变事实**，只改表达。发现内容缺失时是提问用户，不是自己补
- 模拟评审**不突破红线**。不许为了提分编数字
- 用户明确说"就这样吧"，立刻停止迭代
- 不要把模拟评审做成打击。反馈要具体、可执行，指向文本而不是指向人
